GP-TARS V2 / Intelligence Architecture

Self Learning & Continuous Improvement

TARS learns from conversations, teaching sessions, corrections and physical experience while keeping important software and safety changes controlled, testable and reversible.

01

Design principle

Learn continuously; change deliberately

TARS should become more useful through shared experience without blindly rewriting its own production software. Most improvement occurs through inspectable memory, user models, learner models, behavioural policies and robot-experience data. Code changes move through a separate test-and-approval pipeline.

03

Layer 1

Personal memory

TARS can remember useful facts, relationships, preferences, projects and prior interactions for each person. Every durable memory should carry owner, confidence, source, timestamp, privacy classification, importance and expiry/retention metadata. Casual conversation must not automatically become permanent truth.

Corrections are first-class events. When a person says TARS is wrong, the old memory is retained as superseded/auditable rather than silently overwritten.

04

Layer 2

Adaptive teaching

TARS maintains learner-specific skill models. It records concepts attempted, confidence, mistakes, successful teaching approaches and retention over time. A child or adult can therefore resume approximately where they left off rather than beginning every session from zero.

learner.skill
  concept: multiplication.eight_times_table
  confidence: 0.32
  strengths: [multiples_of_5, multiples_of_10]
  preferred_methods: [visual_groups, repeated_addition]
  next_review: spaced_repetition

Periodic low-pressure retrieval checks can update confidence and trigger a short lesson when useful. Teaching behaviour remains age-appropriate and subject to the identity/personality rules documented elsewhere.

05

Layer 3

Behaviour learning

TARS can measure which interaction patterns work for each person: answer length, technical depth, guided questions, teaching format, interruption frequency and successful explanations. These observations update an inspectable behaviour policy rather than modifying the foundation model itself.

06

Layer 4

Robot experience

TARS learns about its physical system from telemetry and outcomes: floor type versus slip, gait versus energy consumption, actuator temperature, calibration drift, microphone performance by environment, vision performance, navigation failures and successful routes. Experience can tune bounded operating parameters but cannot override safety limits.

Significant code, model, motion, safety, permission and infrastructure changes require human approval. TARS may generate a patch or pull request and supporting evidence, but production deployment remains governed.

08

Reflection

Idle / nightly learning cycle

When idle, tars-reflection reviews recent interactions and telemetry to identify durable memories, uncertain facts, learner progress, repeated failures and improvement opportunities. Reflection should summarise evidence rather than hallucinate lessons from sparse data.

09

Forgetting

Memory decay and consolidation

Long-term memory is curated using importance, confidence, recency, frequency of use and ownership. Low-value episodic details decay or are summarised. High-value relationships, explicit preferences and repeatedly confirmed knowledge persist. Users must be able to inspect, correct and delete their personal memories.

10

People teaching TARS

Shared experience

A person can explicitly enter a teaching session. TARS can combine speech, OAK-D vision and contextual events to create a draft procedure or knowledge entry from a demonstrated task. The result is reviewed before becoming a trusted skill. This allows TARS to recall how its own household or workshop performs a task rather than relying only on generic model knowledge.

11

Services

Software components

tars-learning owns learner/user adaptation and experience updates. tars-reflection performs consolidation, anomaly review and improvement proposals. tars-memory stores episodic, semantic and user-owned memories with pgvector/PostgreSQL. tars-core consumes the resulting context and policies. GitHub/GHCR remains the governed route for production software changes.

12

Non-negotiable boundaries

Safety and governance

The LLM and learning services never gain direct authority to bypass the safety MCU, E-stop, actuator limits or deterministic motion controller. Learned motion parameters remain bounded. Production self-modification is prohibited outside the test, review and deployment pipeline. Sensitive personal information is isolated by user and access policy rather than becoming shared global memory.
